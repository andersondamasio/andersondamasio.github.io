Temporal: um dia de calendário e 24 horas são contratos diferentes

Responsável pelo site: Anderson Damasio. Conteúdo produzido com apoio de IA. Critérios editoriais.

Publicado em: 17/02/2026 05:48

Atualização editorial em 10/10/2026: requisitos e conclusões revistos com fontes oficiais. A data da publicação original foi preservada.

Uma data de vencimento sem horário, um instante registrado em UTC e uma reunião em um fuso específico representam informações diferentes. Antes de escolher a operação de soma, é preciso decidir qual dessas informações a aplicação está modelando. Temporal torna essa distinção explícita, mas não escolhe a regra de negócio por você.

A documentação do TC39 distingue PlainDate, para uma data de calendário sem horário ou fuso, Instant, para um ponto na linha do tempo, e ZonedDateTime, que associa data e horário a um fuso. Objetos com prefixo Plain não carregam um fuso implícito. Fonte: tipos de Temporal.

As notas do Chrome 144 registram a chegada da API ao navegador. Isso não comprova suporte em todos os navegadores, WebViews ou ambientes Node.js usados por uma aplicação. Fonte: notas do Chrome 144.

Um dia de calendário não é sempre 24 horas

A documentação de ZonedDateTime diferencia aritmética de calendário da soma de unidades de tempo. Também oferece disambiguation para resolver ou rejeitar horários locais repetidos ou inexistentes nas transições de fuso. A opção reject permite tornar essas ambiguidades um erro explícito. Fonte: aritmética e desambiguação de ZonedDateTime.

O exemplo sintético abaixo compara as duas operações e rejeita horários ambíguos. Ele usa a implementação nativa do navegador; não implementa regras de fuso por conta própria.

'use strict';

function compararDatas(temporal = globalThis.Temporal) {
  if (!temporal?.PlainDate || !temporal?.ZonedDateTime) {
    throw new Error('Temporal indisponivel neste ambiente.');
  }
  const inicio = temporal.PlainDate.from('2026-02-13');
  const seteDiasDepois = inicio.add({ days: 7 });
  const partida = temporal.ZonedDateTime.from('2026-03-07T12:00[America/New_York]');
  const diaSeguinte = partida.add({ days: 1 });
  const rejeitaHorario = texto => {
    try {
      temporal.ZonedDateTime.from(texto, { disambiguation: 'reject' });
      return false;
    } catch (erro) {
      if (!(erro instanceof RangeError)) throw erro;
      return true;
    }
  };
  return {
    dataOriginal: inicio.toString(),
    seteDiasDepois: seteDiasDepois.toString(),
    partida: partida.toString(),
    diaSeguinte: diaSeguinte.toString(),
    horasTranscorridas: diaSeguinte.since(partida, { largestUnit: 'hours' }).hours,
    apos24Horas: partida.add({ hours: 24 }).toString(),
    horarioInexistenteRejeitado: rejeitaHorario('2026-03-08T02:30[America/New_York]'),
    horarioRepetidoRejeitado: rejeitaHorario('2026-11-01T01:30[America/New_York]')
  };
}

if (typeof module !== 'undefined') module.exports = { compararDatas };

Código completo de comparação. Carregado como script em um ambiente com Temporal, execute compararDatas(). Sem suporte à API, a função informa o erro; não converte silenciosamente os valores para Date.

Codex executou o código no Chrome 154.0.8037.99, sem requisições externas. O resultado foi:

{
  "dataOriginal": "2026-02-13",
  "seteDiasDepois": "2026-02-20",
  "partida": "2026-03-07T12:00:00-05:00[America/New_York]",
  "diaSeguinte": "2026-03-08T12:00:00-04:00[America/New_York]",
  "horasTranscorridas": 23,
  "apos24Horas": "2026-03-08T13:00:00-04:00[America/New_York]",
  "horarioInexistenteRejeitado": true,
  "horarioRepetidoRejeitado": true
}

O avanço de um dia manteve o horário local ao atravessar a transição representada pelas regras de Nova York e correspondeu a 23 horas transcorridas. A soma de 24 horas chegou às 13h. O valor original de PlainDate permaneceu inalterado depois da soma de sete dias. O ensaio também conferiu a rejeição de uma data inválida com overflow: 'reject' e a falha explícita quando Temporal está ausente.

Traduza o resultado para o contrato da aplicação

  • Se o campo é apenas uma data de vencimento, não acrescente um horário UTC só para caber no tipo escolhido.
  • Se a regra exige exatamente 24 horas transcorridas, teste esse intervalo. Se exige o mesmo horário local no dia seguinte, teste a operação de calendário e as transições relevantes.
  • Para uma entrada local sem offset que possa ser ambígua, defina como pedir esclarecimento ao usuário. Rejeitar a entrada é uma política possível, não uma resposta universal.
  • Documente o formato persistido e o significado dos campos. A adoção de um tipo no front-end não migra automaticamente contratos de API, banco de dados ou integrações.

Antes de adotar, confira suporte nos ambientes realmente atendidos. Detectar a existência de Temporal é uma verificação inicial, não uma suíte de compatibilidade. Uma alternativa de biblioteca ou polyfill exige decisão e testes próprios; nenhuma foi adicionada neste exemplo.

Limites do ensaio

São casos sintéticos executados por Codex, não relatos de Anderson em produção. O ensaio usa as regras de fuso disponíveis no navegador informado; não cobre todos os calendários, futuras alterações dessas regras, outros navegadores, recorrência de agenda ou migração de dados. Não houve benchmark. O texto anterior atribuía experiência pessoal ao autor e sugeria adoção em projetos novos como solução para compatibilidade; essas conclusões foram retiradas.
