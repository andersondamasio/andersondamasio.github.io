Plain Vanilla: quando um elemento HTML substitui um componente

Responsável pelo site: Anderson Damasio. Conteúdo produzido com apoio de IA. Critérios editoriais.

Publicado em: 11/05/2025 15:43

Atualização editorial em 10/10/2026: requisitos e conclusões revistos com fontes oficiais. A data da publicação original foi preservada.

Reduzir dependências no front-end começa por identificar o comportamento necessário. Uma seção de perguntas e respostas, por exemplo, pode precisar apenas de um controle para revelar conteúdo. Isso é diferente de autenticar usuários, armazenar dados ou expor uma API no servidor.

O projeto Plain Vanilla explica desenvolvimento com HTML, CSS e JavaScript, sem frameworks ou ferramentas de build. O material aborda componentes, estilos, sites e aplicações; seu ponto de partida é a plataforma web. Fonte: apresentação do Plain Vanilla.

Um exemplo que pertence ao problema

A versão anterior deste artigo apresentava um trecho em C# como criação de uma API. Ele fazia uma requisição HTTP como cliente: não declarava um endpoint nem atendia requisições. Também havia marcação HTML dentro do código. Esse exemplo foi removido porque não demonstrava a abordagem de front-end discutida pela fonte.

Para revelar um trecho de conteúdo, HTML oferece details, com summary como resumo do controle. O atributo booleano open representa o estado aberto; escrever open="false" não é uma forma de fechá-lo, pois o atributo continua presente. Fonte: elemento details na MDN.

O fragmento abaixo usa esse controle nativo, sem manipulador de clique nem dependência de JavaScript:

<details>
  <summary>Como pedir uma corre&ccedil;&atilde;o?</summary>
  <p>Envie o endere&ccedil;o do artigo e o trecho a revisar.</p>
</details>

Fragmento HTML em texto simples. Ele pode ser inserido em uma página existente; não é um documento completo com cabeçalho, navegação e estilos.

Codex verificou esse fragmento no Chrome 154.0.8037.99, com JavaScript da página desativado: começou fechado, abriu com clique, fechou com Enter e abriu com Espaço. Esse resultado demonstra somente o comportamento observado desse controle nesse navegador.

O que avaliar antes de remover uma dependência

Escreva o contrato do componente atual antes de substituí-lo. Além de abrir e fechar, ele pode controlar foco, restaurar estado, validar permissões ou carregar conteúdo remoto. A alternativa nativa só atende ao recorte que você efetivamente comparou.

  1. Liste as interações de teclado e ponteiro usadas hoje. Compare estados aberto e fechado, foco visível e leitura do conteúdo, incluindo os navegadores e recursos assistivos do público.
  2. Separe o que pertence à interface do que exige servidor. Esconder um bloco visualmente não protege informação confidencial nem implementa autorização.
  3. Compare a manutenção necessária: código removido, comportamento que precisou ser recriado e testes que continuam necessários. Contar pacotes, sozinho, não mede esse custo.
  4. Se o objetivo inclui desempenho, meça a mesma tarefa antes e depois, com condições registradas. Este exemplo não mede carregamento, memória ou tempo de resposta de uma aplicação.

Uma mudança pequena permite voltar à implementação anterior caso uma interação se perca. Não há obrigação de retirar o framework de toda a aplicação para usar um elemento nativo em um trecho.

Limites

O teste foi executado por Codex para esta revisão, não é vivência profissional atribuída a Anderson. Não houve migração de projeto real, auditoria completa de acessibilidade, teste com leitor de tela nem benchmark. O título anterior sugeria uma experiência pessoal de sucesso e retrabalho que não foi confirmada; essa atribuição foi retirada. A escolha arquitetural depende dos requisitos que o fragmento não cobre.
